# ADR-016 — Localization and Calendar

- Status: Accepted
- Date: 2026-08-15

## Context

محصول باید برای کاربران فارسی‌زبان و انگلیسی‌زبان قابل استفاده باشد. نمایش تاریخ در فرهنگ فارسی با تقویم شمسی و در فرهنگ انگلیسی با تقویم میلادی انتظار می‌رود. ذخیرهٔ فنی باید یکسان و قابل‌مقایسه بماند.

## Problem

چگونه UI دوزبانه و دو تقویم را پیاده کنیم بدون دو مدل داده و بدون وابستگی دامنه به فرهنگ کاربر؟

## Options

1. **فقط فارسی + شمسی**  
   ساده. کاربر انگلیسی‌زبان و گزارش‌های بین‌المللی ضعیف می‌شوند. خلاف تصمیم محصول.

2. **دوزبانه با ABP Localization (`fa` / `en`) + تقویم وابسته به Culture**  
   متن‌ها در JSON resource هر ماژول. `fa` → RTL + Jalali در UI. `en` → LTR + Gregorian در UI. ذخیره: `DateOnly` / `DateTimeOffset` میلادی UTC در SQL.

3. **دو فیلد تاریخ در DB (شمسی و میلادی)**  
   همگام‌سازی شکننده؛ گزارش و مقایسه سخت.

4. **کتابخانهٔ i18n جدا از ABP**  
   تکرار زیرساختی که ABP دارد.

## Decision

**گزینه ۲.**

- فرهنگ‌ها: `fa` (پیش‌فرض UI برای استقرار ایران) و `en`
- تعویض زبان در runtime (کوکی/پروفایل کاربر) طبق ABP Localization
- `fa`: `MudRTLProvider` + `AppDatePicker` شمسی
- `en`: LTR + DatePicker میلادی
- دامنه و DB هرگز تاریخ شمسی ذخیره نمی‌کنند
- اعداد و پیام اعتبارسنجی از resource همان فرهنگ

## Consequences

- مثبت: یک منبع حقیقت برای تاریخ؛ گزارش و Job بدون وابستگی به UI
- مثبت: هم‌خوان با ABP و MudBlazor RTL
- منفی: هر DatePicker باید از `AppDatePicker` برود نه کنترل خام Mud
- منفی: تبدیل Jalali فقط در لایهٔ UI / application display؛ تست تبدیل اجباری است
